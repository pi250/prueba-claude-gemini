# Revisión de código (Gemini) — 2026-10-29 09:30

Proyecto: conversor de temperaturas Celsius ↔ Fahrenheit (`convertir_temperatura.py`).

## Revisión original de Gemini

### Veredicto
Aprobado con cambios — El proyecto está limpio, bien estructurado y sin dependencias innecesarias, pero presenta un bug de precisión en coma flotante en el límite del cero absoluto en Fahrenheit y tests de CLI que no verifican la salida generada.

### Problemas críticos
Ninguno.

### Problemas importantes
1. **`convertir_temperatura.py` (función `convertir`): falso positivo por precisión de punto flotante en el cero absoluto en Fahrenheit (`-459.67 °F`).**
   - Según Gemini, `fahrenheit_a_celsius(-459.67)` produce `-273.15000000000003`, que es menor que `-273.15`, y se lanzaría `ValueError` para el valor exacto del cero absoluto en °F. Además, con origen F y destino C, `fahrenheit_a_celsius(valor)` se calculaba dos veces.
   - Corrección propuesta: definir el cero absoluto por escala (`{"C": -273.15, "F": -459.67}`), comparar en la escala de origen y no convertir dos veces.

2. **`test_convertir_temperatura.py` (clase `TestCLI`): los tests de CLI no verifican `stdout`/`stderr`.**
   - Solo comprobaban el código de retorno. Propuesta: capturar la salida con `contextlib.redirect_stdout` / `redirect_stderr` y comprobar el texto, `--decimales` y el destino por defecto.

### Sugerencias menores
1. **`main`: anotación de tipos incompleta** en `argv`. Propuesta: `Optional[Sequence[str]]` (o `list[str] | None`).
2. **`main`: la validación de `--decimales` está fuera de `argparse`** y devuelve código `1`, mientras que el resto de errores de argumentos devuelven `2`. Propuesta: validador en `type=` que lance `argparse.ArgumentTypeError`.
3. **`README.md`: bloques de código sin especificar lenguaje** (comandos sin ```` ```bash ````).

### Puntos fuertes
- Diseño modular y testeable (lógica pura separada del parser y del `main`).
- Buena defensa ante entradas inválidas (NaN, inf, minúsculas, bajo cero absoluto).
- Cero dependencias externas.

## Cambios aplicados

**Importantes (aplicados):**
- **Cero absoluto por escala.** Ahora se valida en la escala de origen con `CERO_ABSOLUTO = {"C": -273.15, "F": -459.67}`, y ya no se convierte antes de validar (se elimina el cálculo duplicado). Nota: al reproducir el caso en el sandbox con el código original, `-459.67 °F` **no** fallaba (devolvía `-273.15`), así que el síntoma concreto descrito no se pudo confirmar. Aun así, el cambio es válido porque elimina la dependencia del redondeo en el límite y la doble conversión. Se añadió el test `test_cero_absoluto_exacto` para ambos límites.
- **Tests de CLI.** Se reescribió `TestCLI` capturando `stdout`/`stderr` y verificando el texto exacto, `--decimales`, el destino por defecto y el código de salida. Se pasó de 11 a 14 tests.

**Menores:**
- Anotación de tipos de `main` (aplicada, con `Optional[Sequence[str]]` por compatibilidad con Python 3.8).
- Validación de `--decimales` en `argparse` (aplicada, con `decimales_valido`). Consecuencia: un valor negativo ahora termina con código `2` y muestra el uso, de forma coherente con el resto de errores de argumentos. Se documentó en el README.
- Bloques de código del README (**descartada**): el README ya usaba bloques ```` ```bash ````; la observación se debió, probablemente, a que el contenido le llegó a Gemini sin las vallas de código.

**Extra:** se añadió `.gitignore` (`__pycache__/`, `*.pyc`, `.env`) y el README documenta los códigos de salida y el cero absoluto en °F.

**Verificación:** `python -m unittest` → 14 tests OK; ejecución manual de `-459.67 --de F` y `100 --de C --a F` correcta.
